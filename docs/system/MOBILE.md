# The native Android app (`apps/mobile`)

Since Oct 13, 2026 Talorys has a **real native Android app** — React Native through Expo (SDK 57,
expo-router, TypeScript), not a WebView and not a PWA wrapper. Yishai chose it over a TWA at 13:31
Oct 13 ("the PWA feels like a web app, not native"). It talks to the **same agent Worker API** the
web app uses, through the Pages `/api` proxy, so nothing is duplicated server-side.

Package id: **`dev.talorys.app`**. The first APK (`bot.tab.talorys.yishai`, a WebView wrapper with
its own key) was retired on Oct 13, 2026 — its source, key and download page are deleted; on a phone
that still has it, uninstall it (the two can sit side by side).

## What it is

| Area | How |
| --- | --- |
| Screens | Login (server address + owner password) → **bottom tabs Home · Chat · Projects** (v0.3.0, see "v0.3.0: Home, one chat, projects" below). Settings (Appearance, Language, Notifications, Model, Connections, Account, About) opens from Home's header; Memory / Tasks / Notes / Automations / Connections from Home's shortcuts. Pushed screens use native stack transitions; Android Back pops them. |
| Chat | FlashList, memoized rows; the streaming reply lives in its own store so each token re-renders **one row**, never the list. Markdown (`react-native-markdown-display`) for finished messages, plain text while streaming. Tool calls as chips; approval cards with Approve / Decline; connect cards (OAuth link or secure API-key fields) — same endpoints as the web. Haptics on send / approve. Keyboard-aware composer. |
| Design | The approved mockups: Inter (Latin) + Heebo (Hebrew), the neutral grey tokens with the placeholder accent (`#4C47E0` / `#8F8CFF`), radii 10/14/20/28, Lucide icons, light / dark / system (Settings → Appearance, persisted per device). Edge-to-edge, themed status and navigation bars, splash + adaptive icon from the web icon. |
| Hebrew | Strings ported from `apps/web/src/lib/i18n.tsx` (`src/lib/strings.json`, every key in both languages, tested). Language = device (auto) / עברית / English. Hebrew flips the whole app to RTL through `I18nManager.forceRTL` — Android applies that on the next start, so the Settings row says to restart after a change. The drawer opens from the start edge (the right in Hebrew). |
| Auth | The agent's session, as a bearer token kept in the Android keystore (`expo-secure-store`). `POST /api/auth/login` with header `x-talorys-client: native` returns `{ token }` instead of setting the cookie; every call sends `Authorization: Bearer …` (`apps/agent/src/api/middleware.ts`, `readSessionToken`). Same CSRF header as the web. |
| Streaming | `expo/fetch` (streaming bodies; React Native's own fetch buffers) + the same SSE framing as the web (`src/lib/api.ts`, unit-tested). |
| Model picker | Settings → Model reads `GET /api/ai/models` (the Settings worker's catalog, grouped by provider, with free/paid, tools, speed, quality, context tags), `PATCH /api/settings { modelProvider, model }` to choose, `PUT/DELETE /api/ai/keys/:provider` + `test` for Gemini / OpenRouter keys (masked, never echoed). An older agent without `/api/ai/models` shows the current model read-only. From v0.1.3 a "Model chain" row opens `settings/chain.tsx`: the whole fallback chain with status and quota left, reorder (↑/↓), remove, add a model or an OpenAI-compatible endpoint (MODELS.md, "Chain editor and quota view"). |
| Push | Native (FCM) — see NOTIFICATIONS.md "Native push" and below. |

Source layout: `src/app` (routes), `src/components`, `src/lib` (api, session, chat store, theme, i18n,
push), `plugins/withReleaseSigning.js` (release signing from env vars), `scripts/build-apk.sh`,
`tests/` (vitest: SSE parser, streaming reducer, i18n, keyboard, recovery, signing plugin; `scripts/check-routes.cjs` guards the route tree). `android/` is generated by `expo prebuild`
and **not committed** (Continuous Native Generation); `google-services.json` is gitignored too.

## v0.3.0: Home, one chat, projects (Oct 28, 2026)

Yishai asked for the app to feel like the Hark app: three bottom tabs, one chat that knows
everything, and projects with their own chats. The drawer and the list of conversations are gone.

| Tab / screen | What it does | Agent endpoints |
| --- | --- | --- |
| **Home** (`(main)/index.tsx`) | Greeting + date, settings gear. **Weather** for the phone's approximate location (`WeatherCard`, `lib/weather.ts`, `lib/location.ts`): Open-Meteo, no key; current temperature + condition, today's high / low, "feels like", the place name from Android's geocoder. The location prompt is shown **once**, from the card's Allow button (never on launch); denied → a line saying how to turn it on + "Open settings", never a re-ask. **Notifications** (newest 4, expand to 30, unread dot, Mark all read; a tap marks it read and opens its `updates-*` thread with the full text). **Today & upcoming**: open tasks due today or overdue (tick to complete; a tap opens Tasks, or the project's Tasks tab) plus reminder automations firing in the next 48 h (tap → Automations). **Suggested for you**: proactive suggestions with *Do it* (marks accepted, puts the suggestion in the main chat's composer and switches to Chat) and *Dismiss*. Shortcuts row. Pull to refresh; refreshes on focus. The Home tab shows the unread count as a badge. | `GET /notifications`, `POST /notifications/read`, `GET /tasks?view=today`, `GET /automations`, `GET /suggestions?status=new`, `PATCH /suggestions/:id` |
| **Chat** (`(main)/chat.tsx`) | **One continuous chat** — agent thread `main` (created on first use). Notifications are shown **inline**, merged by time (last 7 days, `lib/threads.ts` `mergeNotices`); a tap opens the notification's `updates-*` thread. The empty state is the old greeting + prompt tiles. | `GET /conversations/main`, `POST /chat {conversation_id:"main"}` |
| **Projects** (`(main)/projects.tsx`) | Active / paused / completed projects with open-task counts; archived ones folded below. **+** creates (name + description). Long-press → Rename / Archive (Restore) / Delete. | `GET /projects`, `POST /projects`, `PATCH /projects/:id`, `DELETE /projects/:id` |
| Project (`projects/[id].tsx`) | Segments **Chat · Tasks · Notes**. Chat is thread `project-<id>`, whose prompt carries the project's tasks and notes. Tasks: add inline, tick, delete. Notes: create / edit / long-press delete. ⋯ menu: rename (+ description), archive, delete. | `GET /projects/:id` (project + tasks + notes + thread id), `GET /conversations/project-<id>`, `/tasks`, `/notes` |
| Thread (`chat/[id].tsx`) | A pushed chat with Back: the `updates-*` thread a push tap or an inline notice opens. `/chat/main` redirects to the Chat tab. | `GET /conversations/:id` |
| Connections (`settings/connections.tsx`) | **Connected services** (logo, account, Disconnect with confirm) and **Supported services** (search in English or Hebrew, Connect). OAuth → the consent page in a browser tab (`expo-web-browser`), then the screen polls until the connection appears (60 s, then "check again"). API-key / custom-credential services → a secure form with the connector's own fields; the values go to the agent and on to OpenConnector, never stored or shown again. Services whose OAuth app is not registered say they need a one-time setup. | `GET /connections`, `GET /connections/catalog` (now with `he` and `logo`), `GET /connections/:service/plan`, `POST /connections/:service/connect`, `GET /connections/:service`, `DELETE /connections/:service` |

**How "knows everything" works (agent, `apps/agent/src/agent/threads.ts`).** `main` and
`project-<id>` are fixed-id threads created on first read or message. Each turn in `main` adds a
"Live context for this chat" section to the system prompt: notifications from the last 3 days
(title + excerpt, unread marked), automation runs that failed, the next scheduled automations,
tasks due today / overdue, active projects with open-task counts, and open suggestions — on top of
the memories and the running summary every conversation already gets. A project thread's section is
that project's description, open and recently completed tasks and notes, and tells the model to file
new tasks and notes under that project.

**Notifications and the main chat — the choice.** Shown inline, not mirrored. Every notification
is still written to its own `updates-*` thread (commit 6e8a034) and the push still points there,
so a tap opens the full text exactly as before. The main chat *displays* recent notifications
between its messages (client-side), and the agent's digest describes the same notifications, so
"what about that reminder?" in `main` works. Mirroring them into `main`'s history was rejected: it
would put runs of assistant-only turns into the model's history (some providers reject or merge
consecutive assistant turns) and grow `main`'s summary with automation output.

**Push taps:** the thread id (`data.thread`; older agents: `conversation_id` or `url` `/chat/<id>`)
`main` → the Chat tab; `project-<id>` → that project's screen; anything else (`updates-*`, an
approval's chat) → the thread screen. Routing lives in `lib/notificationRouting.ts` (pure, tested in
`tests/notification-routing.test.ts`) and `lib/useNotificationRouting.ts`.

**The notification blink loop (0.2.3 / 0.3.0, fixed in 0.3.1).** Once pushes carried a thread id
(agent 6e8a034), tapping one while the app was closed made it blink until force-closed. The tap was
routed at mount, before the session was read. Every screen sits behind a `Stack.Protected` guard
that is still false then, so the app's root Stack renders nothing and the only mounted navigator is
expo-router's internal outer stack (`__root`, `+not-found`, `_sitemap`). `router.push("/chat/<id>")`
diverged there and became `PUSH __root {screen: "chat/[id]"}` — a second copy of the whole root
layout, which started not-ready again, got the same response from `getLastNotificationResponseAsync()`,
pushed another `__root`, and so on. (A tap while the app was already open and signed in routed into
the app's own stack and worked.) 0.3.1 collects taps at mount but navigates only when the session
is ready and signed in **and** the app navigator is mounted (`appNavigatorMounted`), handles each
notification once by request identifier (persisted, plus `clearLastNotificationResponse()`), uses
`router.navigate` instead of `push`, and stops routing for good if taps ever produce more than 3
navigations in 10 s. Server side, the agent's FCM payload no longer carries `conversation_id` or a
`/chat/<id>` url (the thread is in `data.thread`, the url is `/chat?thread=<id>`), so an installed
0.2.3/0.3.0 opens on its home screen instead of looping, and 0.3.1 still opens the thread.
expo-router itself does nothing with notifications (no `+native-intent`, no handling of `data.url`).

**Keyboard above the tab bar.** The Chat tab's column ends at the tab bar, which the keyboard
covers, so the spacer is `keyboard − (tab bar + nav inset)` when open and 0 when closed
(`composerBottomSpace(..., offset)`, tested in `tests/keyboard.test.ts`). Pushed chats (threads,
a project's chat) keep the old rule.

**Not changed:** the web app keeps its conversation list (the new threads simply appear in it, titled
"Talorys" and the project's name). Old conversations are still on the server; the app no longer lists
them (they open from a push or a link).

## CI build (GitHub Actions)

`.github/workflows/mobile-apk.yml` builds the signed APK on `ubuntu-latest` (Node 22, JDK 17,
platform 36 / build-tools 36.0.0 / NDK 27.1.12297006 / cmake 3.22.1, `TALORYS_GRADLE_XMX=3072m`
for R8). Trigger: **workflow_dispatch**, or a pushed tag **`native-v*`** (adds a GitHub prerelease
with the APK). Repository-agnostic: it runs wherever the secrets exist (the plan is Tab's
`theyishaik-lab/talorys`, pulling from `yishaik/talorys` main). Secrets: `TALORYS_KEYSTORE_BASE64`,
`TALORYS_KEYSTORE_PASSWORD`, `TALORYS_KEY_ALIAS`, `GOOGLE_SERVICES_JSON_BASE64` (required — the job
stops with a list of what is missing), `TALORYS_KEY_PASSWORD` (optional, defaults to the keystore
password). It runs typecheck, lint and tests, decodes the keystore into `$RUNNER_TEMP` and
`google-services.json` into `apps/mobile/`, runs `scripts/build-apk.sh`, checks the signature with
`apksigner verify --print-certs`, deletes the decoded files and uploads
`talorys-native-<version>-<versionCode>.apk` as an artifact. **The keystore must be the one the
installed app was signed with** (0.2.3 / versionCode 5 was built from 91bef96 with Yishai's key),
or Android refuses the update.

## Build (local, no EAS)

```bash
cd apps/mobile && npm install --legacy-peer-deps   # separate package, not a workspace (its own React Native tree)
npm run typecheck && npm run lint && npm test
export ANDROID_HOME=~/android-sdk   # platform 36, build-tools 36.0.0, ndk 27.1.12297006, cmake 3.22.1 (sdkmanager), JDK 17
export TALORYS_KEYSTORE_PATH=… TALORYS_KEYSTORE_PASSWORD=… TALORYS_KEY_ALIAS=talorys
./scripts/build-apk.sh          # expo prebuild + gradle assembleRelease → android/app/build/outputs/apk/release/app-release.apk
```

- First build compiles the native modules (Reanimated, Screens, Gesture Handler, SVG, Worklets…) —
  about 25 minutes on 4 CPUs and **2–3 GB of RAM**; later builds reuse `.cxx` and take ~5 minutes.
  The script builds **arm64-v8a only** (every phone since 2017; add `armeabi-v7a` for old ones).
- R8 (minify + resource shrinking) is **on** (`app.json` → `expo-build-properties`): the APK is
  ~39 MB. R8 needs heap: at `-Xmx1536m` it died with "GC overhead limit exceeded"; `-Xmx3072m`
  (the script's default since v0.1.3, `TALORYS_GRADLE_XMX` overrides; run it when nothing else heavy runs on the box)
  builds it in ~2 min. Everything else builds fine at 1.5 GB.
- Yishai's keystore: `/home/user/tab/state/talorys-mobile-keystore/talorys-release.jks` on Tab's box,
  alias `talorys`, password in `talorys-secrets.json` → `mobile_keystore` (never in git). **Losing it
  means the next APK cannot update the installed app** — it would have to be uninstalled first.
- Version: `expo.version` / `android.versionCode` in `app.json`; bump `versionCode` every release.
  Released: `native-v0.1.0` = versionCode 2 (0.2.0, no Firebase), `native-v0.1.1` = versionCode 3
  (0.2.1, FCM), `native-v0.1.2` = versionCode 4 (0.2.2, keyboard + stream recovery),
  `native-v0.1.3` = versionCode 5 (0.2.3: per-model error attribution and the "ענה: …" note, the model
  chain editor with quota view, Hebrew for task priorities / memory categories / automation kinds and
  schedules), and next `native-v0.1.4` = versionCode 6 (**0.3.0**: tabs, Home, one main chat,
  projects, app-native Connections; built by the CI workflow). The tag counts
  releases (0.1.x); `expo.version` (shown in About) runs one minor ahead (0.2.x) since the first build. Releases live on GitHub (`theyishaik-lab/talorys`, prerelease per tag) because the
  APK (~40 MB) is too big to send as a chat attachment.
- **Metro cannot bundle `@talorys/shared` values.** tsc and vitest resolve the package through aliases,
  Metro does not (and its barrel pulls in zod). `src/` imports only TYPES from `@talorys/shared`; runtime
  helpers come from `src/lib/shared.ts`, which re-exports the dependency-free `attribution.ts` / `chain.ts`
  (`metro.config.js` watches `packages/shared/src`). `tests/shared-runtime.test.ts` fails on a value import.
  Green tsc + tests do not prove the bundle: `npx expo export:embed --platform android --dev false
  --entry-file node_modules/expo-router/entry.js --bundle-output /tmp/b.js --assets-dest /tmp/res` (~40 s)
  does. (v0.1.3's first build died at `createBundleReleaseJsAndAssets` on exactly this, Oct 13, 2026.)
- v0.1.3 build (Oct 13, 2026): 6.5 min with `~/.gradle` already warm, APK 38.2 MB (36.4 MiB), 24 arm64 `.so`.
- `expo prebuild --clean` wipes `android/` (so `.cxx` for the app) but the library builds under
  `node_modules/*/android/build` survive — a rebuild after `--clean` is ~10 min, not 25.
  (Oct 13, 2026 box cleanup: `~/.gradle/caches` and those library builds were cleared, so the next
  build is a first build again — ~25 min plus the Gradle dependency download.)
- `npm run lint` (expo lint, React Compiler rules): fetch-on-mount effects call the loader through
  `Promise.resolve().then(...)`, and `Date.now()` never runs in render (tasks.tsx `renderedAt`).

## Keyboard (Android 15+ edge-to-edge) — v0.1.2

Yishai, 16:17 Oct 13 on v0.1.1 / Pixel 9 Pro: "when the keyboard is open you can't see the text box".
Expo SDK 57 apps are always edge-to-edge, and Android 15+ enforces it: **the window is not resized for
the keyboard** whatever `windowSoftInputMode` says (`softwareKeyboardLayoutMode: "resize"` →
`adjustResize` is still set, it just no longer moves anything). The keyboard is drawn over the app and
reported only as an IME inset; React Native's `KeyboardAvoidingView` with `behavior={undefined}` on
Android therefore did nothing and the composer sat under the keyboard.

How it works now (`react-native-keyboard-controller` 1.21.9, the SDK 57 bundled version):
- `KeyboardProvider statusBarTranslucent navigationBarTranslucent preserveEdgeToEdge` at the root
  (`src/app/_layout.tsx`), so keyboard heights are the **full** IME inset from the screen edge.
- The chat column is `[header][list flex:1][composer][KeyboardSpacer]`. The spacer
  (`src/components/KeyboardSpacer.tsx`) is an Animated.View whose height follows the keyboard frame by
  frame on the UI thread: `max(keyboardHeight, navigationBarInset)` (`composerBottomSpace` in
  `src/lib/keyboard.ts`). Closed → the composer clears the gesture pill / 3-button bar; open → it sits
  flush on the keyboard. The multi-line input grows upward (the list gives up the room).
- The list stays on the latest message: `onScroll` tracks "near the end" (96 dp); while pinned, every
  list resize (keyboard opening, composer growing) calls `scrollToEnd`, plus once on `keyboardDidShow`.
- Login and every `Screen` (Settings → Model's API-key fields) use `KeyboardAwareScrollView`, which
  scrolls the focused field above the keyboard. Connect-card key fields live in the chat list, which
  stays pinned to the end, so the latest card stays above the composer.
- Verified without a device: `tests/keyboard.test.ts` lays out the chat column on a Pixel 9 Pro
  (915 dp, Gboard 336 dp inset, gesture 24 dp / 3-button 48 dp) and checks the composer's bottom edge
  equals the keyboard's top edge at every animation frame, plus wiring checks. Nobody has watched it
  on a phone yet.

## Chat streams on a phone — v0.1.2 (agent 0.1.11-streams)

Yishai, 16:18 Oct 13 on v0.1.1: every message ended in "Software caused connection abort", then
"A response is already being generated in this conversation". Found on his agent: none of the three
turns had a saved answer. Causes and fixes:
- **The app killed its own stream on a new chat.** The home screen moves to `/chat/[id]` as soon as the
  agent names the conversation, and its unmount aborted the request. Now the stores of an in-flight
  turn are registered by conversation id (`inFlight` in `src/lib/chat.ts`), the new screen picks up
  the same stores, and leaving a screen never aborts (only Stop does, through `/chat/cancel`).
- **The agent threw the answer away when the client vanished** (it aborted on the first failed write)
  and a write that stalled kept the conversation claimed. Now writes are never awaited, a dropped
  client no longer stops the turn (it finishes and is saved), a claim with no progress for 150 s is
  released (`STALE_RUN_MS`), and an SSE comment `: ping` goes out every 10 s so a silent model never
  leaves an idle connection for a carrier or proxy to drop. Semantic recall is capped at 3 s.
- **Recovery in the app.** A drop mid-turn ("Software caused connection abort" is Android's text for a
  connection torn down under the TLS read) or a stream that ends without `done` → the row says
  "החיבור נקטע. מביא את התשובה מהשרת…" and the app polls `GET /conversations/:id` every 2 s (up to
  4 min) until `streaming` is false, then shows history. CONFLICT → our bubble says it wasn't sent
  (Hebrew) and the previous answer is fetched. Opening a chat whose reply is still running polls too.
- **Errors in Hebrew.** `src/lib/errors.ts` maps codes and the agent's English messages (busy, daily
  limit, quota, model unavailable, network, generic) to `chat.err.*` strings; unknown text shows as is.
- Measured Oct 13 with OkHttp 4.12 over HTTP/2 (the app's own stack) against his agent: with
  gemini-3.8-flash selected the stream sat **68–71 s silent** before the first word (Google's free tier
  queueing). The drop test (cut the connection right after `start`) left a saved reply and a free
  conversation 2.6 s later.

## Native push (Firebase Cloud Messaging)

The app registers its FCM device token with the agent (`POST /api/push/devices`); the agent sends
through **FCM HTTP v1** signed by the Worker (`apps/agent/src/push/fcm.ts`): service-account JWT
(RS256, WebCrypto) → OAuth access token cached 55 min → `messages:send`. Same triggers and per-device
toggles as Web Push (`approval`, `result`, `reminder`); the two channels live side by side in
`PushService` (`push.native`). Android channels: **approvals** (high importance, vibrates) and
**updates** (default). A tap opens the chat the notification is about (`data.conversation_id`).

Status on this install: **set up Oct 13, 2026** — Firebase project `talorys-app` (free Spark
plan, no billing; a separate project on purpose, because adding Firebase to `talorys-connector`
would have moved that billed project onto Firebase's Blaze pay-as-you-go plan), Android app
`dev.talorys.app` registered, `FCM_SERVICE_ACCOUNT` + `PUBLIC_APP_URL` on the Worker (agent
`0.1.10-fcm`), `google-services.json` and the service-account key kept on Tab's box under
`state/talorys-firebase/` (paths in `talorys-secrets.json` → `firebase_project`). APK
`native-v0.1.1` (versionCode 3) is the first build with it. After sign-in the app asks Android's
notification permission once and registers; Settings → Notifications shows the registered state,
the three toggles and "Send test notification" (the server's FCM answer is shown on failure).

Per-install setup (the thing the PWA never needed):

1. Firebase project on the owner's Google account (add Firebase to the existing GCP project
   `talorys-connector`, or a new one), Android app with package `dev.talorys.app` →
   `google-services.json` → `apps/mobile/google-services.json` (gitignored; `app.json`
   `android.googleServicesFile`). Rebuild the APK.
2. Service account with the "Firebase Cloud Messaging API Admin" role → JSON key →
   `npx wrangler secret put FCM_SERVICE_ACCOUNT --config deploy/agent.wrangler.jsonc` (paste the
   whole JSON). Optional `PUBLIC_APP_URL` var (the web URL deep links point at).
3. `GET /api/push/native` → `enabled: true`. The app's Settings → Notifications toggle now registers.

Without step 2 the routes answer `NOT_CONFIGURED` and the app says so in Hebrew.
Not done yet: Approve / Decline **buttons on the notification itself** (the tray notification is
FCM's own while the app is in the background; buttons need a data-only message + a background task)
— today the tap opens the approval card, one more tap approves.

## The black screen of native-v0.1.0 (fixed in v0.1.1)

Yishai's Pixel 9 Pro opened v0.1.0 to a black screen that never changed and never crashed (15:13
Oct 13). Cause: a scaffold leftover, `src/app/index.tsx` (`<View><Text>Talorys</Text></View>`). In
expo-router a root `index` owns the launch path `/`, ahead of the real home `(main)/index`, and sat
outside the login guard — so every cold start rendered that stub: default black text on the dark
background. `scripts/check-routes.cjs` (part of `npm test`) resolves `/` with expo-router's own
resolver and fails unless it lands on `(main) > index`; with the stray file it printed `index`.
Hardening that came with the fix (`src/components/ErrorScreen.tsx`, `_layout.tsx`): a root
ErrorBoundary and a global JS error handler paint the error text (Hebrew hint, stack, selectable)
instead of a black window; the splash is forced down after 4 s; the preference stores (2.5 s) and the
keystore/session read (6 s) time out into defaults; a "Talorys…" placeholder shows while loading.
Checked on the v0.1.0 APK and ruled out: Hermes bytecode present and matching the engine
(250829098.0.17), all 25 arm64 `.so` files, 16 KB page alignment (`zipalign -c -P 16`).
